# 비품 신청 페이지

두드림원 근무지 리더용 비품 신청 페이지. 기존 구글폼을 대체하는 **화면**이며,
데이터는 그대로 기존 구글폼으로 전송된다.

```
이 페이지 → 구글폼 formResponse → 비품 신청(2026)(응답) 시트 → 텔레그램 알림
                                   └─ 여기부터는 기존 그대로, 손댈 것 없음
```

시트 구조는 `메인`(미처리) → 텔레그램에서 완료 처리 → `완료`(이력).
이 페이지는 어느 쪽도 건드리지 않는다.

## 폴더 구조

```
supply-request/
├── index.html              "주소가 변경되었습니다" 안내 페이지
├── verify.ps1              인증 코드 검증 스크립트
├── links.ps1               근무지별 공유 링크 생성
└── 2026-3q-912f36/
    └── index.html          실제 신청 페이지 (슬롯)
```

슬롯 폴더명을 바꾸면 옛 주소는 404가 되고 새 주소만 살아난다.
이것이 4개월 주기 리더 교체 때 하는 유일한 작업이다.

## 근무지별 링크

리더는 근무지를 고르지 않는다. 링크 자체가 근무지를 담고 있다.

```bash
powershell -ExecutionPolicy Bypass -File supply-request/links.ps1 -User <깃허브아이디>
```

| 근무지 | 주소 뒤에 붙는 값 |
| --- | --- |
| 서관 1 | `?w=seo1` |
| 서관 2 | `?w=seo2` |
| 동관 후문 | `?w=dong-h` |
| 동관 지하 | `?w=dong-b` |
| 신관 지하 | `?w=sin-b` |
| 동관 정문 / 신관 정문 | `?w=jeongmun` |
| (관리자 · 7곳 전부) | 없음 |

근무지가 **1곳**인 링크는 근무 지역 선택 카드가 통째로 사라지고 헤더에 근무지가
못박혀 표시된다. 리더는 물품만 고르면 되고, 다른 근무지로 잘못 신청할 수가 없다.

정문 2곳은 리더가 같아 하나로 묶었다. 이 링크만 근무지 선택이 남지만 선택지가
2개뿐이다. 묶음 구성이 바뀌면 슬롯 `index.html`의 `SITES`를 고친다.

`?w` 값이 없거나 모르는 값이면 7곳 전부 보여준다. 관리자용이자 안전한 폴백이다.

파일은 하나뿐이다. 근무지별로 복사본을 만들지 않으므로 품목이 바뀌어도
한 곳만 고치면 6개 링크에 동시에 반영된다.

## ⚠️ 가장 중요한 것 — 조용한 실패

페이지는 `no-cors`로 전송하기 때문에 **구글이 400으로 거부해도 알 수 없다.**
리더 화면에는 "접수됐어요"가 그대로 뜬다.

구글폼은 `formResponse` 직접 POST에 대해서도 서버에서 검증한다(확인 완료).
필수 항목 누락, 목록에 없는 값, 정규식 불일치 — 전부 **HTTP 400, 행 생성 안 됨.**

즉 폼과 페이지가 어긋나면 **리더 전원이 성공 화면을 보는데 비품은 하나도
나가지 않고, 아무도 눈치채지 못한다.**

그래서 폼과 페이지를 동시에 건드리는 작업 뒤에는 반드시 검증한다.

```bash
powershell -ExecutionPolicy Bypass -File supply-request/verify.ps1
```

`verify.ps1`은 페이지 파일에서 상수를 직접 읽으므로 실제 배포될 코드를 검사한다.
전체 확인(정상 신청까지)은 `-Live`를 붙인다. 시트에 테스트 행이 1개 생기고
텔레그램 알림도 실제로 발송되므로, 끝나면 `메인` 탭에서 그 행을 지운다.

## 인증 코드 — 완료됨

2026-08-07에 설정 완료. 옛 구글폼 주소는 잠겼다.

| 항목 | 값 |
| --- | --- |
| 폼 질문 | `인증 코드` (단답형·필수·정규식 일치, 맨 마지막) |
| 정규식 | `^Q3-912F36$` |
| entry ID | `entry.521168683` |

`verify.ps1 -Live` 3항목 전부 통과 확인:
코드 없음 → 400, 틀린 코드 → 400, 정상 신청 → 200.

아래는 코드를 다시 바꿀 때를 위한 절차다. 평소 4개월 주기 교체에서는
**이 절차를 밟지 않는다** (슬롯 폴더명만 바꾼다).

### 왜 이렇게 했는가

기존 구글폼 주소는 이미 직원들에게 퍼져 있었다. 구글폼에는 "이 주소로는 받지
않고 내 페이지에서 온 것만 받기" 같은 설정이 없고, `응답 받지 않음`을 켜면
이 페이지의 전송까지 막힌다. 그래서 **폼에 인증 코드 질문을 추가**해서 잠근다.

폼을 복제하지 않는 이유: 새 폼을 기존 시트에 연결하면 구글이 새 탭을 만들고
폼 종속 트리거는 따라오지 않는다. 텔레그램이 에러 없이 조용히 멈출 수 있다.
인증 코드 방식은 폼-시트 연결·탭·트리거를 전혀 건드리지 않고 D열 하나만 늘린다.
A~C열이 그대로라 열 번호로 접근하는 코드도 안 깨진다.

### 절차

1. 구글폼 **맨 마지막**에 질문 추가 (마지막이어야 D열로 붙는다)

   | 설정 | 값 |
   | --- | --- |
   | 질문 | `인증 코드` |
   | 유형 | 단답형, 필수 |
   | 응답 확인 | 정규식 → **일치** → `^Q3-912F36$` |
   | 오류 메시지 | `이 주소는 더 이상 사용하지 않습니다. 관리자에게 새 주소를 문의해 주세요.` |

2. 폼 미리보기에서 개발자도구 콘솔에 붙여넣어 새 entry ID 확인

   ```js
   FB_PUBLIC_LOAD_DATA_[1][1].map(q => [q[1], 'entry.' + q[4][0][0]])
   ```

3. 슬롯의 `index.html`에서 두 상수를 채운다

   ```js
   var ENTRY_CODE  = "entry.123456789";
   var ACCESS_CODE = "Q3-912F36";
   ```

4. 검증 — **여기를 건너뛰지 말 것**

   ```bash
   powershell -ExecutionPolicy Bypass -File supply-request/verify.ps1 -Live
   ```

5. 통과하면 커밋·push. 시트에 생긴 테스트 행 삭제.

이 작업이 끝나면 옛 폼 주소는 영구히 죽는다. 이후 4개월 주기 작업에서는
폼을 건드리지 않으므로 조용한 실패 위험에 노출되지 않는다.

## 4개월마다 — 주소 교체

폴더명만 바꾼다. 폼은 건드리지 않는다.

```bash
git -C supply-request mv 2026-3q-912f36 2026-4q-<새 6자리>
```

커밋·push 하면 1~2분 뒤 옛 주소는 404, 새 주소가 살아난다.
그 다음 새 링크를 뽑아 각 근무지 리더에게 자기 링크만 공유한다.

```bash
powershell -ExecutionPolicy Bypass -File supply-request/links.ps1 -User <깃허브아이디>
```

주소 교체는 **인증이 아니다.** 새 주소를 받은 리더가 옛 리더에게 링크를
전달하면 그대로 뚫린다. 4개월 주기 정리에는 맞지만 사람 단위로 막는 수단은 아니다.

인증 코드까지 바꾸고 싶다면(옛 페이지 소스를 저장해둔 사람까지 차단) 위
"1회 작업"의 1~5단계를 다시 밟는다. 이때는 반드시 `-Live` 검증을 거친다.

## 품목이나 근무지가 바뀔 때

슬롯 `index.html`의 `<script>` 상단 배열을 고친다.

| 배열 | 용도 |
| --- | --- |
| `REGIONS` | 근무 지역 목록 |
| `ITEM_ORDER` | 비품 품목 목록 |
| `LAYOUT` | 화면 배치 (아이콘, 장갑 묶음 등) |

**폼을 먼저 고치고 페이지를 맞춘다.** 폼에 없는 값을 보내면 HTTP 400으로
거부되는데 페이지는 성공 화면을 띄운다. 글자 하나까지 똑같아야 한다
(`손소독제(근무지용)`처럼 괄호까지).

`ITEM_ORDER`의 **순서**는 폼의 항목 순서와 같아야 한다. 리더가 어떤 순서로
탭하든 이 배열 순서대로 정렬해 전송하므로, 시트 셀 문자열이 기존 형태로
유지된다(예: `페이퍼 타올, 장갑 S, 장갑 M`). 텔레그램 쪽에서 이 문자열을
파싱한다면 순서가 어긋나는 순간 깨진다.

계절 품목(겨울철 `핫팩` 등)을 넣고 뺄 때도 같은 절차다.
바꾼 뒤에는 `verify.ps1 -Live`로 확인한다.

## 로컬에서 확인

`index.html`을 브라우저로 바로 열면 화면은 보이지만 전송이 막힌다
(`file://`에서는 크로스 오리진 POST 차단). 전송까지 보려면 로컬 서버가 필요하다.

```bash
powershell -Command "$l=New-Object System.Net.HttpListener;$l.Prefixes.Add('http://localhost:8765/');$l.Start();while($l.IsListening){$c=$l.GetContext();$b=[IO.File]::ReadAllBytes((Join-Path $PWD 'index.html'));$c.Response.ContentType='text/html; charset=utf-8';$c.Response.OutputStream.Write($b,0,$b.Length);$c.Response.Close()}"
```

슬롯 폴더 안에서 실행하고 <http://localhost:8765> 로 접속한다.
**로컬 테스트도 실제 신청이다.** 테스트한 행은 시트에서 지운다.

## 알아둘 점

- **저장소는 공개(public)다.** GitHub Pages 무료 플랜 조건이다. 원본 구글폼
  자체가 링크만 있으면 누구나 제출할 수 있는 공개 폼이라 노출 수준은 기존과
  같다. 인증 코드를 켜면 오히려 기존보다 잠긴다.
- **신청자 이름·수량 항목은 없다.** 기존 구글폼에 그 항목이 없기 때문이다.
  추가하려면 폼에 질문을 만들어야 하고, 시트 열이 늘면서 텔레그램 쪽도 같이 봐야 한다.
- 네트워크 실패는 감지된다. 요청이 구글에 닿지 못하면 완료 화면 대신 빨간
  배너와 `다시 시도` 버튼이 뜬다. 다만 **닿았는데 거부당한 경우(400)는
  감지하지 못한다** — 위 "조용한 실패" 항목 참고.
- 리더가 마지막에 고른 근무 지역은 브라우저에 기억된다(localStorage).
